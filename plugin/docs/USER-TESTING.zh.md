# SciDataMAS 用户测试方案

[English](USER-TESTING.md) · [Русский](USER-TESTING.ru.md) · **中文**

本文档面向主持人。其编写方式确保一场 45–60 分钟的测试能在不同参与者之间产出可比的记录，并形成一份清晰的修复清单。

目标**不是**证明插件可以正常工作，而是了解以下几点：

1. 研究者是否理解这个数据湖是做什么用的；
2. 创建 → 校验 → 添加 → 检索的流程在哪些环节会中断；
3. 生成的元数据在科学上是否可信；
4. 面板中哪些信息真正被使用；
5. 人们在把真实数据交给这个数据湖之前还需要什么。

## 1. 会话准备

### 主持人清单

- [ ] DSH Web profile 已启动，且 **Data** 面板可见。
- [ ] 仓库之外已存在一个测试数据湖根目录，例如 `~/data/scidatamas-ut-<participant>`。
- [ ] 至少有一个包含 3–10 个真实文件的示例文件夹（图片、CSV，或两者兼有）。
- [ ] 已为导入任务选定一个小型公开 Zenodo 记录（或跳过任务 6）。
- [ ] 模型路由工作正常（`scidatamas_status` 显示模型可用）。
- [ ] 录屏和记录工具已就绪，并已取得同意。
- [ ] 参与者已就匿名化记录给出书面或口头同意。

### 需要告知参与者的内容

> 我们正在测试一个帮助整理科学数据并生成元数据的研究原型。它还不是成品。这里没有错误答案；我们测试的是工具，不是你。请边想边说，遇到任何不清楚的地方随时停下来。本次测试中请勿使用机密或未发表的数据。

披露当前的限制：

- 面板是只读的；
- S3/Synology 存储尚未实现；
- 表格追加尚未实现；
- 模型可能响应缓慢，或返回格式错误的 JSON；
- 生成的元数据可能有误，必须经过审阅。

## 2. 角色

| 角色 | 职责 |
|---|---|
| 主持人 | 朗读任务、提出中立的追问并控制时间。除非参与者卡住超过 3 分钟，否则不解释界面。 |
| 参与者 | 边想边说，用自己的语言完成任务。 |
| 观察者（可选） | 记录原话、迟疑、错误和时间戳；不进行干预。 |

## 3. 议程（60 分钟）

| 时间 | 环节 |
|---|---|
| 0–5 | 欢迎、知情同意、背景说明 |
| 5–10 | 关于当前数据实践的热身问题 |
| 10–20 | 任务 1：创建数据集 |
| 20–30 | 任务 2：校验并完善模式 |
| 30–42 | 任务 3：添加数据并处理缺失字段 |
| 42–50 | 任务 4：检索数据；任务 5：查看面板 |
| 50–55 | 任务 6（可选）：外部导入或表格数据集 |
| 55–60 | 反馈表与收尾 |

如果参与者进度较慢，可放弃任务 6，但保留反馈环节。

## 4. 热身（5 分钟）

在不展示插件的情况下提问：

1. 你目前把一次实验产生的数据保存在哪里？
2. 你如何记录制备和采集参数？
3. 如果同事要在六个月后复用这个数据集，他需要什么？
4. 通常哪些信息会丢失？
5. 你是否尝试过复用别人的数据集？是什么让你停了下来？

逐字记录参与者的原话。这些原话将成为本次测试后续环节的评估用语。

## 5. 任务

为每个任务记录：开始时间、结束时间、完成情况（是/部分完成/否）、主持人介入次数和原话。

### 任务 1 — 创建数据集（10 分钟）

提示语：

> 为 `<sample folder>` 中的文件创建一个数据集。说明一个文件/行代表什么，以及你打算将数据复用于什么目的。先使用 compact 模式。

观察：

- 参与者是否理解数据集与文件夹的区别？
- 他们是否会主动说明用途（未经提示）？
- 他们是否阅读生成的模式？
- 他们是否注意到保留字段（`id`、`author`、`uploaded_at`、`file_path`、`source_url`）？
- 他们是否要求使用 rich/DAG 模式，原因是什么？

追问：

- “你会删除哪些字段？”
- “对于你自己的复用需求，缺少哪个字段？”
- “`draft` 对你来说意味着什么？”

### 任务 2 — 校验与完善（10 分钟）

提示语：

> 对这个数据集运行辩论式验证（debate validation）。查看报告，并决定要修改什么。

观察：

- 他们是否理解覆盖率（coverage）和“有用字段”？
- 他们是否阅读未回答的问题和待澄清问题？
- 他们是添加字段、重写描述，还是忽略报告？
- 他们是否注意到模式不会被自动修改？
- 他们是否过早地激活数据集？

追问：

- “哪条待澄清问题最有用？哪条是噪音？”
- “你会信任这个覆盖率数字吗？为什么？”
- “怎样能让这场辩论感觉像一位真正的评审人？”

### 任务 3 — 添加数据并处理缺口（12 分钟）

提示语：

> 将 `<second sample subset>` 添加到该数据集。要求助手在提交前展示暂存的元数据。有一个必填字段缺失；请决定如何处理。

观察：

- 他们是否在提交前审阅暂存内容？
- 他们是否理解此时尚未复制任何文件？
- 他们如何提供缺失的值：通过文本、元数据覆盖（metadata override），还是编辑模式？
- 他们是否注意到审计轨迹（audit trail）？
- 提交后他们是否检查激活状态？

追问：

- “如果有一个文件是错的，你会预期发生什么？”
- “你更愿意在面板中编辑暂存内容吗？为什么？”
- “什么能让你在不逐行审阅的情况下放心提交？”

### 任务 4 — 检索（8 分钟）

提示语：

> 用科学条件（而不是文件名）查找数据的一个子集。展示文件路径。

观察：

- 他们是否用语义化的方式表述查询？
- 他们是否检查选中了哪个数据集？
- 他们是否理解过滤/计划（filter/plan）的说明？
- 他们是否信任返回的行？
- 结果为空时他们会怎么做？

追问：

- “如果有 10,000 行，你会有什么不同做法？”
- “除了路径之外，回答还应该包含什么？”

### 任务 5 — 查看面板（5 分钟）

提示语：

> 打开 Data 面板，找到该数据集的模式、校验、样本和事件。

观察：

- 他们是否能找到侧边栏入口？
- 他们最先打开哪个标签页？
- 他们是否理解 scope/required/unit 这几列？
- 他们是否使用 Copy id / Refresh？
- 对于快速核验来说，还缺少什么？

### 任务 6 — 可选：外部导入或表格（5 分钟）

提示 A（导入）：

> 分析一个小型 Zenodo 记录，只导入一种类型的文件。

提示 B（表格）：

> 用这个 CSV 创建一个表格数据集，并描述各列。

仅在时间允许时观察。

## 6. 反馈表

使用 1–5 分制（1 = 非常不同意，5 = 非常同意），随后是开放式问题。

### 感知有用性

1. 这个工具解决了我实际遇到的问题。
2. 生成的模式在科学上看起来是合理的。
3. 辩论报告帮助我改进了模式。
4. 暂存式添加让我对数据更有信心。
5. 经过一些修复后，我会把它用于真实数据集。
6. 我会把它推荐给同事。

### 易用性

7. 我不需要帮助就明白该做什么。
8. 面板中的信息很容易找到。
9. 智能体的解释很清楚。
10. 错误信息告诉了我下一步该做什么。

### 开放式问题

1. 本次测试中最有用的时刻是什么？
2. 最令人困惑的时刻是什么？
3. 哪个字段或问题明显是错的？
4. 在把真实数据交给这个数据湖之前，你还需要什么？
5. 如果只能先改一件事，你会改什么？
6. 你会把它用于图像、表格、光谱、测序，还是其他场景？

### 单一易用性问题（SEQ）

> 总体而言，今天完成这些任务有多容易或多困难？（1 = 非常困难，7 = 非常容易）

## 7. 观察记录表

| 时间 | 任务 | 事件 / 原话 | 严重程度（1–3） | 备注 |
|---|---|---|---|---|
| | | | | |

严重程度：1 = 表面问题，2 = 拖慢任务，3 = 阻塞任务或产生错误结果。

## 8. 成功标准

如果参与者在没有主持人介入的情况下能够做到以下几点，则本次测试算作“成功”：

- 创建一个带有合理模式的草稿；
- 阅读至少一条待澄清问题并据此行动；
- 暂存一次添加，并解释为什么缺失的字段会阻止提交；
- 检索出以语义方式描述的子集；
- 在面板中找到模式/校验/样本。

记录首次创建数据集所需的时间和首次提交所需的时间。这两项比单一的满意度评分更有信息量。

## 9. 隐私与数据处理

- 仅使用示例数据或公开数据。
- 不要记录 API 密钥、凭据或个人数据。
- 对参与者 ID 进行匿名化处理（`P1`、`P2`、……）。
- 将录像和记录存放在约定的位置；在约定期限后删除原始录像。
- 如果参与者提到敏感内容，请停止录制，或标记时间戳以便后续脱敏。

## 10. 需要披露的已知限制

- 面板为只读。
- 尚无 S3/Synology 后端。
- 表格数据集不支持追加新行。
- 不支持检查 Parquet/Excel/HDF5。
- 模型生成可能缓慢、昂贵或出错。
- 一个数据湖同一时间只应供一个 DSH 进程使用。
- 导入的产物会被复制；数据湖不是备份系统。

## 11. 缺陷报告模板

```text
标题：
环境：DSH 版本、模型、操作系统、数据湖根目录
任务：
我做了什么：
我期望什么：
实际发生了什么：
复现步骤：
工具输出 / 截图：
严重程度：表面问题 / 拖慢任务 / 阻塞任务 / 错误结果
我会信任这个结果吗：是 / 否 / 修复后
```

## 12. 测试之后

在 24 小时内：

1. 清理记录，删除敏感内容。
2. 把原话转化为研究结论，而不是功能请求。
3. 为每条结论打标签：理解度、工作流、元数据质量、面板、性能、信任。
4. 按严重程度和出现频率排序。
5. 把前三个问题放入下一轮迭代；不要试图修复所有问题。

一份有用的总结只需一页：哪些做得好、哪些造成了阻塞、下一步要改什么，以及为每项改动提供依据的原话。
